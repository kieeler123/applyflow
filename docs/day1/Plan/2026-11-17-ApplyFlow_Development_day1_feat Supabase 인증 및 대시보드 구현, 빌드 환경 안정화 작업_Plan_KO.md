# ApplyFlow 상세 개발 작업계획서

> **프로젝트:** ApplyFlow --- 취업 준비를 체계적으로 관리하는 웹 서비스\
> **작성 기준일:** 2026-11-17\
> **기술 스택:** Next.js 16(App Router), React, TypeScript, Tailwind CSS
> v4, shadcn/ui, Supabase, Vercel\
> **개발 경로:** `H:\applyflow`\
> **핵심 대상:** 국내 신입·주니어 구직자\
> **목표:** 경험 정리 → 지원서 작성 → 지원 일정 관리까지 이어지는 MVP
> 출시

## 0. 이 문서 사용법

-   `[x]`는 대화에서 완료가 확인된 항목, `[ ]`는 미완료 또는 추가 검증이
    필요한 항목이다.
-   **P0:** MVP 출시 전 필수 / **P1:** MVP 품질 개선 / **P2:** 출시 이후
    확장
-   시간은 **1인 개발 기준의 대략적인 순수 작업 시간**이며,
    학습·디버깅에 따라 달라질 수 있다.
-   각 단계는 **작업 → 검증 → 완료 기준(DoD)** 순서로 진행한다.
-   실제 프로젝트 파일·DB 구조는 이 문서 작성 시 직접 검사한 것이
    아니므로, 이미 구현된 작업은 확인 후 체크한다.

## 3. Phase 1 --- Supabase 데이터 모델 및 보안 설계

**우선순위:** P0 · **예상:** 5\~9시간 · **선행:** Phase 0

### 3.1 공통 데이터 설계

-   [ ] 사용자별 데이터 소유권 기준을 `auth.users.id`로 통일
-   [ ] 각 업무 테이블에 `id`, `user_id`, `created_at`, `updated_at`
    정의
-   [ ] 삭제 정책 결정: MVP는 실제 삭제, 복구 필요 시 soft delete 검토
-   [ ] 상태값은 체크 제약 또는 enum 중 하나로 일관성 있게 설계
-   [ ] 날짜·시간 저장 기준 정리: DB는 UTC, 화면은 한국 시간 기준 표시
-   [ ] 인덱스 설계: `user_id`, 마감일, 지원 상태, 생성일

### 3.2 제안 테이블

#### 1. `experiences` — 경험 보관함
- **기본 정보:** `id`, `user_id`, `title`
- **활동 정보:** `organization`, `role`
- **활동 기간:** `start_date`, `end_date`
- **경험 내용:** `situation`, `task`, `action`
- **성과 및 회고:** `result`, `reflection`
- **기록 관리:** `created_at`, `updated_at`

#### 2. `experience_tags` — 경험 태그
- **기본 정보:** `id`, `user_id`
- **경험 연결:** `experience_id`
- **태그:** `name`

#### 3. `applications` — 채용 지원 관리
- **기본 정보:** `id`, `user_id`
- **지원 기업:** `company_name`, `position`
- **채용 공고:** `posting_url`, `deadline_at`
- **지원 현황:** `status`, `memo`
- **기록 관리:** `created_at`, `updated_at`

#### 4. `application_questions` — 지원서 문항 및 답변
- **기본 정보:** `id`, `user_id`
- **지원서 연결:** `application_id`
- **문항 및 답변:** `question`, `answer`
- **정렬 및 수정:** `sort_order`, `updated_at`

#### 5. `question_experiences` — 문항과 경험 연결
- **기본 정보:** `id`, `user_id`
- **문항 연결:** `question_id`
- **경험 연결:** `experience_id`

### 3.3 SQL 마이그레이션 및 RLS

-   [ ] Supabase SQL Editor 또는 CLI 마이그레이션 방식 결정
-   [ ] 테이블 생성 SQL 작성
-   [ ] 외래키 및 삭제 시 동작(`ON DELETE`) 설정
-   [ ] 사용자별 RLS 활성화
-   [ ] SELECT/INSERT/UPDATE/DELETE에 `auth.uid() = user_id` 정책 적용
-   [ ] 관계 테이블은 연결 대상도 동일 사용자 소유인지 검증
-   [ ] 타 사용자 ID로 조회·수정·삭제 시도 테스트
-   [ ] 클라이언트에 `service_role` 키가 노출되지 않도록 확인
-   [ ] DB 스키마 기반 TypeScript 타입 생성 방법 결정

**완료 기준(DoD):** 각 사용자가 자신의 데이터만 읽고 수정할 수 있으며,
다른 사용자의 데이터는 DB 수준에서 차단된다.

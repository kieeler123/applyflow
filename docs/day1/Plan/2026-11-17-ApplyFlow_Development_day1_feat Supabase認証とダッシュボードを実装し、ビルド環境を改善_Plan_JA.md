# ApplyFlow 詳細開発作業計画書

> **プロジェクト:** ApplyFlow --- 就職活動を体系的に管理するWebサービス\
> **作成基準日:** 2026-11-17\
> **技術スタック:** Next.js 16（App
> Router）、React、TypeScript、Tailwind CSS
> v4、shadcn/ui、Supabase、Vercel\
> **開発パス:** `H:\applyflow`\
> **主な対象ユーザー:** 韓国の新卒・若手求職者\
> **目標:** 経験の整理 → 応募書類の作成 →
> 応募スケジュール管理を一体化したMVPのリリース

## 0. この文書の使い方

-   `[x]` はこれまでのやり取りで完了が確認できた項目、`[ ]`
    は未完了または再検証が必要な項目を示す。
-   **P0:** MVPリリース前に必須 / **P1:** MVPの品質向上 / **P2:**
    リリース後の拡張
-   所要時間は**個人開発を想定した実作業時間の概算**であり、学習やデバッグによって変動する。
-   各フェーズは **作業 → 検証 → 完了条件（DoD）** の順に進める。
-   実際のソースコードやDB構造を直接検査したわけではないため、実装済みの項目は確認後にチェックする。

#### 1. アカウント
**MVPに含める（P0）**
- メールでの登録・ログイン

**リリース後（P2）**

- アカウント連携

#### 2. 経験ストック
**MVPに含める（P0）**

- 検索・絞り込み

**リリース後（P2）**
- AIによる経験抽出
- 添付ファイル

#### 3. 応募書類
**MVPに含める（P0）**
- 応募書類のCRUD
- 設問ごとの回答
- 経験との紐付け
- 下書き保存

**リリース後（P2）**
- AIによる下書き・添削

#### 4. 応募スケジュール
**MVPに含める（P0）**

- 締切の管理

**MVPに含める（P0）**

**リリース後（P2）**

### 推奨開発順序

`基盤の安定化 → DB・RLS → 経験ストック → 応募書類 → 応募スケジュール → ダッシュボード統合 → テスト → デプロイ`

## 3. Phase 1 --- Supabaseデータモデルとセキュリティ設計

**優先度:** P0 · **目安:** 5～9時間 · **前提:** Phase 0

### 3.1 共通データ設計

-   [ ] データの所有者を `auth.users.id` に統一
-   [ ] 各業務テーブルに `id`、`user_id`、`created_at`、`updated_at`
    を定義
-   [ ] 削除方針を決定：MVPでは物理削除、復元が必要なら論理削除を検討
-   [ ] ステータス値はCHECK制約またはenumで一貫して管理
-   [ ] 日時の保存基準を整理：DBはUTC、画面は韓国時間
-   [ ] `user_id`、締切、応募ステータス、作成日時のインデックスを設計

### 3.2 提案テーブル

#### 1. `experiences` — 経験ストック
- **基本情報:** `id`, `user_id`, `title`
- **活動情報:** `organization`, `role`
- **活動期間:** `start_date`, `end_date`
- **経験内容:** `situation`, `task`, `action`
- **成果・振り返り:** `result`, `reflection`
- **記録管理:** `created_at`, `updated_at`

#### 2. `experience_tags` — 経験タグ
- **基本情報:** `id`, `user_id`
- **経験との関連:** `experience_id`
- **タグ:** `name`

#### 3. `applications` — 応募管理
- **基本情報:** `id`, `user_id`
- **応募先:** `company_name`, `position`
- **求人情報:** `posting_url`, `deadline_at`
- **応募状況:** `status`, `memo`
- **記録管理:** `created_at`, `updated_at`

#### 4. `application_questions` — 設問と回答
- **基本情報:** `id`, `user_id`
- **応募書類との関連:** `application_id`
- **設問・回答:** `question`, `answer`
- **表示順・更新:** `sort_order`, `updated_at`

#### 5. `question_experiences` — 設問と経験の紐付け
- **基本情報:** `id`, `user_id`
- **設問との関連:** `question_id`
- **経験との関連:** `experience_id`

### 3.3 SQLマイグレーションとRLS

-   [ ] Supabase SQL EditorまたはCLIによるマイグレーション方式を決定
-   [ ] テーブル作成SQLを記述
-   [ ] 外部キーと削除時の動作（`ON DELETE`）を設定
-   [ ] ユーザー単位のRLSを有効化
-   [ ] SELECT/INSERT/UPDATE/DELETEに `auth.uid() = user_id`
    のポリシーを適用
-   [ ] 関連テーブルでは紐付け先も同一ユーザーの所有物か検証
-   [ ] 他ユーザーのIDを使った閲覧・変更・削除の拒否をテスト
-   [ ] `service_role` キーがクライアントに露出しないことを確認
-   [ ] DBスキーマからTypeScript型を生成する方法を決定

**完了条件（DoD）:**
各ユーザーが自分のデータのみ閲覧・変更でき、他ユーザーのデータはDBレベルで遮断される。
